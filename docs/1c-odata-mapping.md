# Обследование OData 1C_VAK — 2026-10-29

Адрес: `http://localhost/1C_VAK/odata/standard.odata/`.
Выполнены только GET-запросы. Сервисный документ и `$metadata` прочитаны;
получены ограниченные выборки справочников, спецификации с 10 строками состава
и отчёта производства. Данные в 1С и PostgreSQL приложения не изменялись.
Полная синхронизация ещё не реализована.

**Обновление 2026-10-30.** Реализована синхронизация справочников единиц, видов
номенклатуры и номенклатуры (`POST /api/integrations/1c/sync`, страница «Данные 1С»)
в таблицу `onec_records`. Проверено на этой базе: 19 единиц, 14 видов, 8 649 записей
номенклатуры (391 помечена на удаление, 111 папок, 8 148 действующих позиций).
У 71 действующей позиции нет действующей единицы, у 196 — действующего вида.
Повторная синхронизация дубликатов не создаёт; при ошибке сохраняется прежний снимок.
При лимите сеансов учебной версии запрос повторяется (5, 15, 30 с).
Синхронизация также сохраняет `specs` (спецификации с составом) и `main_specs`
(действующая основная спецификация на позицию: последняя запись регистра с наступившим периодом).

**Перенос в техкарты** (`POST /api/integrations/1c/import`, `dry_run` по умолчанию true;
сервис `app/services/onec_import_service.py`). Переносятся основные спецификации
с выходом в штуках (целое число) в папку `<цех>/1С/Продукция/<группы 1С>`, компоненты —
в `<цех>/1С/Сырьё/<группы 1С>`. Единицы по коду ОКЕИ: 166 кг, 168 т, 163 г → вес;
112 л, 111 мл → объём; 796 шт → штуки. Строки в других единицах (м, упак — упаковка)
пропускаются. Позиции в группе «Удаленные» не переносятся. Связи хранятся в `onec_links`:
повтор ничего не дублирует; рецептура обновляется, только если изменилась в 1С и не
редактировалась в приложении (иначе — конфликт в отчёте); исчезнувшие из 1С продукты
скрываются (`is_active=false`).

Результат на 2026-10-30 (цех «Производство»): 439 продуктов, 328 ингредиентов,
4 401 шаг, 99 папок. Пропущено: 386 — продукция удалена в 1С, 143 — выход не в штуках
(кремы, тесто, полуфабрикаты в кг — следующий этап, нужен дробный выход/заказ),
89 — группа «Удаленные», 4 — спецификация удалена/чужая.
Таймеры, голосовые шаги и проверки веса из 1С не приходят — добавляются вручную.

**Выход в килограммах** (миграция `a7c3e9f1b246`). У продукта есть `yield_unit`
(`pcs`/`kg`), `products.base_quantity` и `order_lines.quantity` — `Numeric(12,3)`.
Для штучной продукции количество в заявках и выход обязаны быть целыми (проверяет
сервер, `quantity_service.normalize_quantity`); для килограммовой — до граммов.
Единицу продукта с заявками менять нельзя (409), чтобы не пересчитать старые заявки.
Перенос из 1С: выход 796 → `pcs` (только целый), 166 → `kg`. Хэш штучных рецептур
не изменился, поэтому повторный перенос оставил 439 прежних без изменений и добавил
142 рецептуры в кг (32 новых ингредиента, 751 шаг). Не переносится только
«Сахарный сироп 1 л» (выход в литрах).

**Сверка списания сырья** (`GET /api/integrations/1c/reconciliation?date_from&date_to`,
страница «Сверка сырья», сервис `app/services/onec_reconcile_service.py`). Документы
читаются из 1С за период (фильтр по `Date` на сервере проверен: счёт совпал с полной
выгрузкой), в БД не сохраняются. Норма: проведённые `ОтчетПроизводстваЗаСмену`
(кроме `НеОтражатьВОтчетахПоСырью`) × спецификация из строки `Продукция`, брак включён,
по `СкладСырья`. Факт: проведённые `ТребованиеНакладная` по `Склад`, с разбивкой по
основанию (`ДокументОснование_Type`: отчёт производства / акт приёма-передачи).

Что выяснено на октябре 2026: требование по отчёту создаётся одно на отчёт (флаг
`Норма`), но точно совпадает с расчётом по спецификации только у ~110 из 386 —
количества правятся после создания. ~170 требований оформляются по актам
приёма-передачи в тех же цехах; без них общее отклонение −5,5%, с ними −1,8%.
23 проведённых отчёта без требования. 43 строки отчётов без спецификации.
`ДокументОснование` — составного типа: фильтр `ДокументОснование_Key` в OData не работает.

**Стоимость в сверке.** Факт в тенге — точная себестоимость из проводок требований:
`AccountingRegister_Типовой/RecordsWithExtDimensions(StartPeriod, EndPeriod, Condition='AccountCr_Key eq guid''…''')`
по счетам из строк требований (`СчетБУ_Key`, обычно 1310 «Сырьё и материалы»; субконто:
1 — номенклатура, 2 — склад, 3 — партия). У виртуальной таблицы нет постраничного чтения,
а границы периода включительные, поэтому период читается окнами по 2 дня с удалением дублей.
Проверка: по каждому требованию количество в проводках должно совпасть со строками,
иначе его стоимость не учитывается, а требование выводится отдельно.
Цена = средняя себестоимость списания за период по складу (иначе по материалу);
норма и отклонение в тенге = количество × цена. Строки, списанные с нулевой суммой
(в основном собственные полуфабрикаты), цены не дают: их сырьё уже учтено в отчётах
об их выпуске. Октябрь 2026: списано 74 040 692,83 ₸ (совпало с суммой проводок),
перерасход против нормы ≈ +1,66 млн ₸.

## Первый этап: справочники и рецептуры

| Объект OData | Назначение |
|---|---|
| `Catalog_Номенклатура` | Общий справочник продукции и сырья; `Ref_Key`, `Description`, `Parent_Key`, `IsFolder`, `DeletionMark`, `БазоваяЕдиницаИзмерения_Key`, `ВидНоменклатуры_Key`, `ВесХлебов` |
| `Catalog_ВидыНоменклатуры` | Классификация продукции, материалов и прочих объектов. Проверить конкретные значения и ссылки; не классифицировать только по названию |
| `Catalog_КлассификаторЕдиницИзмерения` | Единицы количества, необходимые для перевода в граммы, миллилитры или штуки приложения |
| `Catalog_СпецификацииНоменклатуры` | Рецептуры: `Owner_Key` ссылается на продукцию, `Количество` задаёт базовый выход |
| `Catalog_СпецификацииНоменклатуры_ИсходныеКомплектующие` | Состав: `Ref_Key` спецификации, `LineNumber`, `Номенклатура_Key`, `Количество`; состав также читается вложенной коллекцией спецификации |
| `InformationRegister_ОсновныеСпецификацииНоменклатуры` | Выбор основной спецификации по продукции и периоду: `Period`, `Номенклатура_Key`, `СпецификацияНоменклатуры_Key`. Нужна актуальная на выбранную дату запись, а не случайная спецификация |

Спецификации описывают состав и количество. Они не заменяют технологические
шаги приложения: таймеры, голосовые подтверждения и проверки веса нужно сохранить
отдельно. Поле `ВесХлебов` нельзя применять как коэффициент без проверки его
единицы и бизнес-смысла.

Продукт приложения сейчас имеет целочисленный `base_quantity` и предполагает
выход в штуках. В прочитанной строке документа 1С встречается дробное количество
`11.025`. Поэтому единицу выхода нужно проверить до импорта и при необходимости
расширить модель; округление до штук недопустимо.

## Цеха и склады

- `Catalog_ПодразделенияОрганизаций`: подразделения, `Склад_Key`,
  `СкладГотовойПродукции_Key`. Не каждое подразделение является цехом.
- `Catalog_Склады`: складские ссылки. Не следует превращать каждый склад в цех.
- `InformationRegister_ЗП_СоответствиеПродукцииПодразделению`: возможный
  дополнительный источник соответствия. В схеме есть водитель и коэффициент,
  поэтому назначение регистра нельзя автоматически считать маршрутом производства.

## Последующие этапы

- `Document_ОтчетПроизводстваЗаСмену` и коллекция `Продукция`: факт выпуска,
  подразделение, склады, смена, бригада, спецификация. Это не подтверждённый
  источник будущих производственных заданий. Прочитанный документ не проведён.
- `Document_ТребованиеНакладная` и коллекция `Материалы`: расход сырья.
- `AccountingRegister_Типовой` / регистры движения: источник официальных
  остатков требуется отдельно определить по счетам и аналитикам конфигурации.
  Остатки ещё не проверены; нельзя вычислять их только из нескольких документов.
- Явного опубликованного документа производственного заказа по именам объектов
  не обнаружено. Источник плановых заявок требует обследования; существующий
  ввод/импорт заявок проекта пока сохраняется.

Зарплата, налоги, банковские и кадровые данные не нужны для первого этапа.

## Правила интеграции и ограничения проверки

1. Сохранять соответствие источника и `Ref_Key` идентификаторам приложения.
   Название не является ключом; повторная загрузка не должна создавать дубликаты.
2. Проверять ссылки состава, единицы и выбранную основную рецептуру до активации.
3. Сначала синхронизировать чтение. Запись/проведение документов — отдельный этап
   с проверкой бизнес-логики и защитой от повторной операции.
4. Числа `odata.count` при фильтрации не считать проверенными итогами импорта:
   запрос с `DeletionMark eq false` вернул для номенклатуры строку с
   `DeletionMark: true`; для складов/подразделений фильтр вернул ноль, хотя
   запрос без фильтра возвращал строки с `DeletionMark: false`.
   Причина не установлена. Проверить кодирование пробелов, семантику фильтра
   и непосредственно значения каждой записи; не объявлять справочники пустыми.
5. Последующие запросы получили HTTP 400 с явным текстом:
   `Достигнуто ограничение учебной версии. Достигнуто предельное количество подключений к ИБ`.
   Успешная публикация OData не доказывает отсутствие ограничений учебной версии.
   Для дальнейшей проверки выполнять запросы последовательно и учитывать другие
   сеансы. Полнота чтения всей базы пока не подтверждена.
